# Поддержка картой и СБП в MAX и Telegram

Подготовлена интеграция **ЮKassa**. Реальный магазин ещё не подключён;
оплата отключена без реквизитов. Telegram принимает Stars независимо от ЮKassa.
При отключённой ЮKassa MAX не показывает кнопку поддержки, команды оплаты в
профиле или раздел оплаты в справке. Уже отправленные главные меню обновляются
на месте, с сохранением приветственной картинки. Старые callback-кнопки не могут
создать новый заказ при отключённом магазине.

При включении магазина Telegram добавляет кнопку «Карта / СБП» в `/donate`, рядом
с суммами Stars. `/donate card` открывает рублёвое меню; `/donate 250 card` и
`/donate 250 sbp` создают разовый заказ. Условия: `/terms card`; обращение или
возврат: `/paysupport card <вопрос>`. `/donations` показывает собственные платежи
обоих видов; выключение магазина не скрывает сохранённые квитанции.

`/donate` показывает 100, 250, 500 и 1000 ₽, карта или СБП. Пользователь переходит
на страницу ЮKassa; бот не получает данные карты. Произвольная сумма 100–10000 ₽:
`/donate 250 card` или `/donate 250 sbp`. Поддержка добровольная, разовая, без
подписки, сохранения карты и повторных списаний. Чтение бесплатно.

Оплата только в личном чате владельца заказа. `/donations` показывает его квитанции,
тестовые платежи и возвраты явно отмечены. `/terms` — условия/контакт.
`/paysupport <вопрос>` сохраняет частное обращение; просьба о возврате не запускает
возврат автоматически.

## Магазин

В приватном `.env`:

```dotenv
YOOKASSA_ENABLED=true
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
YOOKASSA_RETURN_URL=https://<домен>/max/payments/return
PAYMENT_SUPPORT_CONTACT=<контакт для вопросов и возвратов>
```

Нужны все четыре заполненных поля и `YOOKASSA_ENABLED=true`. Для отключения без
удаления секретов установите `YOOKASSA_ENABLED=false`. После изменения `.env`
пересоздайте `bot`, `worker`, `maxbot` и `max-web` через `docker compose --profile
max up -d --no-deps --force-recreate bot worker maxbot max-web`. Новое окружение
применяется при запуске служб; это не горячая перезагрузка `.env`. Фоновое
обновление существующих главных меню MAX выполняется с ограничением скорости.
Для Telegram также должен работать общий HTTPS-приёмник `max-web`: он принимает
подтверждения обоих ботов по одному адресу уведомлений.

Поддержка не продаёт цифровой контент и не открывает платных функций. Telegram
Stars остаются отдельным способом; [правила Telegram для цифровых товаров и
услуг](https://core.telegram.org/bots/payments-stars) требуют Stars для таких продаж.

Настроить карты, СБП, назначение платежей и применимый режим чеков в кабинете.
Интеграция не придумывает налоговые ставки или контакт для чеков. Если магазин
требует дополнительные данные, отказ API остаётся отказом, а не квитанцией.
До реального запуска проверить требования магазина и тестовый платёж/возврат.
Секрет маскируется в логах.

В кабинете ЮKassa настроить события `payment.succeeded`, `payment.canceled`,
`refund.succeeded` на `https://<домен>/max/payments/yookassa`. API управления
подписками требует OAuth, поэтому с обычным shopId/secret_key бот его не вызывает.

## Проверка и восстановление

Заказ и UUID `Idempotence-Key` сохраняются до API. Повтор потерянного ответа
использует те же данные и UUID. Параллельное создание заказа сериализовано advisory
lock без открытой транзакции на сетевой вызов. После получения payment_id — GET.

Webhook — подсказка: авторизованный GET ЮKassa сверяет магазин, UUID заказа,
назначение и платформу, сумму, RUB, способ оплаты, статус и тестовый режим. Поддельное `paid: true`
не подтверждает платёж. Неизвестный объект не вызывает GET. HTTP 200 выдаётся после
проверки и фиксации; сбой API/БД просит повторную доставку.

Квитанция и уведомление создаются одной транзакцией; повтор webhook не создаёт
вторую благодарность. Старый `pending` не откатывает успешную оплату. Страница
возврата не подтверждает платёж. Отдельная сверка раз в минуту восстанавливает
пропущенные уведомления и справедливо обходит ожидающие заказы.

ЮKassa гарантирует идемпотентность 24 часа. Бот прекращает POST без provider ID
через 23 часа: старый потерянный ответ требует сверки в кабинете, чтобы не создать
второй платёж. Известный ID безопасно запрашивается снова. Автоматическая сверка
ограничена 7 днями; старые случаи разбирает оператор.

## Оператор на VPS

Только локально, без публичного HTTP admin API:

```sh
docker compose exec maxbot python -m app.native_payment_admin history
docker compose exec maxbot python -m app.native_payment_admin support
docker compose exec maxbot python -m app.native_payment_admin reconcile
docker compose exec maxbot python -m app.native_payment_admin refund <order-UUID>
docker compose exec maxbot python -m app.native_payment_admin verify <order-UUID> <payment-UUID>
```

`verify` привязывает найденный потерянный платёж после GET и полной сверки.
`refund` делает полный возврат успешного платежа; постоянный UUID защищает от
повторного возврата. Исходная квитанция сохраняется, статус возврата подтверждает
API. Частичные возвраты не реализованы. Обращения содержат личный текст,
их нельзя публиковать в Git.

Миграция 021 помечает прежние заказы как `max`, а новые Telegram-заказы —
`telegram`. Пользователи, владельцы заказов и квитанции двух платформ проверяются
отдельно. Подтверждённое уведомление попадает в транспорт исходного бота.
