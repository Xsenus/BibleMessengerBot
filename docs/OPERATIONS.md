# Эксплуатация

## Проверки

```bash
docker compose ps
docker compose logs --tail=100 bot worker admin
bash diagnose.sh
docker compose run --rm --no-deps bootstrap python -m app.cli audit
```

Логи приложения редактируют секреты, но перед передачей диагностики всё равно просмотрите её. Не отправляйте `.env`, backup или Telegram-переписку. `/health` — живость web-процесса, `/ready` — готовность БД. Bot/worker обновляют heartbeat; отказ проверки означает необходимость разбора, не доказанное отсутствие проблем.

## Неопределённая отправка

`/status [target]` показывает задания. `uncertain` означает, что приложение не может доказать, получил ли Telegram конкретную часть. Сначала откройте сам канал/чат и сравните с заданием, затем администратор отправляет:

```text
/resolve 123 sent @your_channel
/resolve 123 retry-duplicate-risk @your_channel
/resolve 123 cancel @your_channel
```

`sent` — считать спорную часть доставленной и продолжить оставшиеся; `retry-duplicate-risk` — повторить спорную часть с осознанным риском дубля; `cancel` — отменить остаток. Решение записывается в operator_events. Команда применяется и к остановленным failed-заданиям, когда нужна явная развязка. При частичной отправке изменение языка/прогресса блокируется; завершите или отмените задание. Нельзя удалять запись delivery_log и предполагать, что это «исправило» публикации.

`/pause` сохраняет подтверждённые части и прогресс. `/resume` продолжает только не подтверждённые части, кроме неопределённых заданий. `/unsubscribe` явно отменяет публикации; не вызывает автоматическое решение спорной доставки. После восстановления из старого backup возможна рассинхронизация с уже опубликованным Telegram: остановите worker и проверьте состояние вручную.

## Резервная копия

```bash
sudo bash backup.sh
```

Используется pg_dump custom-format, атомарное завершение, права600 и SHA256. Скопируйте файл и `.env` в защищённое независимое место. Backups содержат персональные ID, прогресс и сообщения; не кладите их в публичный Git.

```bash
# Заменяет БД целиком. Сначала проверьте путь и сервер!
sudo bash restore.sh backups/YOUR_BACKUP.dump --confirm-replace-data
```

Скрипт сначала проверяет pg_restore list и делает копию текущей БД, останавливает службы, восстанавливает в транзакции, применяет миграции, проверяет данные и запускает службы только после успеха. Сценарий в среде подготовки не выполнялся. Нужна учебная проверка восстановления на отдельном хосте до принятия production.

## Обновление/добавление редакций

Сохраните `.env`, сделайте backup, меняйте BIBLE_PROFILE/MAX_EDITIONS_PER_LANGUAGE в `.env`, выполните `sudo bash install.sh`. Для ручного импорта сначала остановите все службы, использующие shared maintenance guard:

```bash
docker compose stop bot worker admin
docker compose run --rm --no-deps bootstrap python -m app.cli import --profile extended --max-editions 2
docker compose run --rm --no-deps bootstrap python -m app.cli audit
docker compose up -d --no-deps bot worker admin
```

Последнюю команду выполняйте только после успешного аудита. `--refresh` перечитывает закреплённую ревизию, а не новую main. Не меняйте исходную ревизию/уже применённые SQL вручную. Если обновление оборвалось, службы должны оставаться остановленными до устранения причины.

## Приёмка после первого запуска

Откройте/start и/settings в личном чате; выберите два разных языка в двух тестовых группах, проверьте отсутствие влияния друг на друга. Протестируйте смену издания, часового пояса, одну длинную главу, паузу/продолжение и отписку. Сравните несколько ссылок и диапазонов с конкретным исходным изданием. Запланируйте по одной тестовой публикации. Проверьте запрет изменения неадминистратором, потерю прав бота и выбранную forum topic. Эти действия не были выполнены разработчиком без вашего токена и доступов.
