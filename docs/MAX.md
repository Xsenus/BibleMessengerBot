# MAX: перенос полного набора возможностей

Статус версии 1.18.1 на 9 октября 2026: **код подготовлен, работающий MAX-бот ещё не активирован**.
Токен установлен на VPS и проверен через GET `/me`; профиль и 22 команды подтверждены
API. Локальный `max-web` healthy. Публичная доставка событий ещё не подключена:
порт 443 используется существующим VPN. Telegram продолжает использовать текущий транспорт.

## Устройство

Библия, поиск, рендеринг, планы чтения, картинки, озвучка, молитвы и ограничения расходов
используются совместно. Пользователи, чаты, сообщения и загруженные в мессенджер файлы
имеют отдельную идентификацию. Совпадение числового MAX ID с Telegram ID не объединяет
аккаунты. Прогресс, язык и подписки каждого чата независимы.

Миграция `018_max_platform.sql` добавляет поля `platform` со значением `telegram` для
существующих записей и отдельные таблицы MAX. Названия `telegram_users`, `telegram_chats`
и колонок внутренних ссылок сохранены для совместимости старых миграций и сервисов;
для MAX эти числа — внутренние ключи, не реальные Telegram ID.

`platform_identities` сопоставляет внешние MAX ID с независимыми внутренними ключами.
В личном диалоге внутренний ключ чата равен ключу его владельца; перепривязка к другому
пользователю запрещена. Внешний строковый MID хранится в `max_messages`; редактирование
проверяет одновременно бота, чат и локальный ключ сообщения. `max_media` хранит повторно
используемые MAX upload tokens отдельно от Telegram file IDs. Перед каждым повторным
использованием проверяется, что исходная картинка не была забракована.

`max_inbox` сохраняет события до подтверждения Webhook и дедуплицирует повторную доставку
по ID сообщения/callback. Ограничение размера события — 64 КиБ. `max_rate_limits`
независим от Telegram: консервативно 10 сообщений/с суммарно и 1 сообщение/с в один чат.
Потеря подтверждения отправки означает неопределённый результат; новая отправка того
же сообщения автоматически не повторяется. Повтор фиксированного редактирования безопасен.

## Особенности API MAX

Используется актуальный адрес `https://platform-api2.max.ru` и заголовок
`Authorization: <token>` без `Bearer` и без query token. TLS-проверка обязательна;
`MAX_CA_FILE` при необходимости добавляет доверенный сертификат к системному набору.
Для production MAX требует Webhook через HTTPS на порту 443; Long Polling предназначен
для разработки. Текст запроса ограничен 4000 символами.

Аудио и файлы должны быть единственным вложением сообщения. Поэтому озвучка будет
доступна через кнопку и отдельное аудиосообщение; картинка и кнопки остаются в карточке.
Исходные WebP-изображения преобразуются в JPEG только при загрузке в MAX; проверенный
файл в БД не изменяется. Авторизационный заголовок API не передаётся на CDN-загрузчик.

Источники: [обзор API](https://dev.max.ru/docs-api),
[Long Polling](https://dev.max.ru/docs-api/methods/GET/updates),
[Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions),
[медиа](https://dev.max.ru/docs-api/use-cases/sending-messages/media),
[официальная OpenAPI-схема](https://github.com/max-messenger/api-schema/blob/main/schema.yaml).
Проверены 9 октября 2026; схема уточняет, что audio/file — единственное вложение.

## Конфигурация и проверки

Переменные перечислены в `.env.example`: `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`,
`MAX_WEBHOOK_URL`, необязательный `MAX_CA_FILE`. Токены, секреты, ID реальных пользователей
и содержимое их сообщений не публикуются в документации или тестовых фикстурах.

Тесты `test_max_client.py`, `test_max_events.py`, `test_max_ui.py` проверяют реальные формы
HTTP-запросов через изолированный MockTransport, ошибки/неопределённые ACK, загрузку
JSON-фото/XML-аудио, отсутствие утечки Authorization, клавиатуры и входные события.
`test_max_postgres.py` использует отдельную временную БД: совпадающие внешние ID,
сохранение настроек, запрет перепривязки, точность редактирования и повторные Webhook.
Без `RUN_DB_TESTS=1` проверки БД явно пропускаются; их нельзя считать пройденными.

Проверка первого этапа: [CI коммита `ddb205e`](https://github.com/Xsenus/BibleMessengerBot/actions/runs/37885860757)
завершён успешно — **898 passed, 122.02 с**, без пропусков. Включены 50 новых проверок
протокола/транспорта/кнопок и четыре проверки на реальном PostgreSQL с изолированными
временными базами. Этот результат относится к первому этапу. Проверка текущей версии отражается в
[VALIDATION.md](VALIDATION.md); живая проверка диалога ещё ожидает подключение Webhook.

## Активация

На VPS системные корни не доверяют сертификату `platform-api2.max.ru`.
Подготовить отдельный публичный CA:

```sh
python scripts/prepare_max_ca.py
```

В `.env` задать `MAX_CA_FILE=/app/certs/max-ca.pem`. Каталог `certs` доступен только
для чтения в MAX и worker; не входит в Git/образ. Скрипт загружает по проверенному
HTTPS официальный сертификат с Госуслуг, проверяет закреплённый SHA-256 DER
`d26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31`.
Смена сертификата требует проверки источника/отпечатка. Системное доверие и другие
API не меняются, `verify=False` не используется. Источник:
[Госуслуги](https://www.gosuslugi.ru/crt),
[публичный CA](https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt).

Дополнительно миграции 019–020 добавляют платформу карточек, отметку предложенной
озвучки, последовательную входную очередь и независимый журнал RUB-платежей.
Перед миграциями остановить все изменяющие БД службы, сделать проверенную
зашифрованную резервную копию и использовать штатный bootstrap. Применённые
миграции не редактировать: контроль SHA-256 сохранён.

Настроить DNS и сертификат HTTPS на 443, проксировать три пути `/max/...` из
`deploy/max.nginx.conf.example` на локальный `127.0.0.1:8081`; панель операций не
публиковать. Задать `MAX_WEBHOOK_URL=https://<домен>/max/webhook` и секрет от 32
случайных URL-safe символов. `MAX_HOST_PORT` меняет только локальный порт.
После bootstrap и запуска общих служб:

```sh
docker compose --profile max up -d max-web maxbot
```

Домен не обязателен при наличии доверенного сертификата с IP в SAN.
[Let’s Encrypt поддерживает IP-сертификаты](https://letsencrypt.org/2026/03/11/shorter-certs-certbot.html)
с профилем `shortlived` и сроком 160 часов; требуются автоматическое продление
и перечитывание сертификата. Подготовлены [скрипт и таймер обслуживания](MAX_HTTPS.md),
ACME `--dry-run` проверен на VPS. Регистрация IP URL в MAX и реальная доставка событий
должны быть проверены отдельно, получение сертификата само по себе их не доказывает.

Если 443 уже обслуживает Xray REALITY, отдельный nginx stream со `ssl_preread`
может передавать TLS с именем сервера VPN в действующий Xray, а TLS без SNI
или с IP-адресом — в HTTPS-приёмник MAX. Проверка 9 октября на отдельных локальных
портах прошла, включая настоящий VLESS REALITY-сеанс; публичная маршрутизация
не изменялась. Это не универсальная конфигурация для любых VPN: сначала проверить
используемые SNI и маршруты, затем согласовать изменение работающего сервиса.
Без прозрачного проксирования Xray увидит IP шлюза вместо IP клиента.

`max-web` проверяет схему и credentials. Heartbeat `maxbot` появляется после
GET `/me`, установки меню и регистрации webhook. Чужой webhook автоматически
не удаляется. Профиль `app/data/max-profile.json` и PNG в `assets/brand` установить
через MAX для бизнеса: текущий API управляет меню, но не именем/описанием/аватаром;
возможна повторная модерация. [Официальные сведения](https://dev.max.ru/help/chatbots).

В личном диалоге `/chats` показывает известные чаты, где у пользователя есть права
администратора. `/settings chat:123` и остальные команды управления принимают
положительный или отрицательный внешний ID; права проверяются заново. Управление
чужим личным чатом запрещено. Темы форума Telegram в MAX отсутствуют.

Подсказки `/time` и кнопки времени в личном диалоге не содержат внутреннего ID.
Для удалённого чата они показывают пригодный для копирования внешний `chat:<ID>`.
Команды с упоминанием другого бота игнорируются, включая помощь и платежи.

Прерванные входящие события получают `uncertain` и требуют операторской проверки;
автоматического повторного выполнения после аварии нет. `/status` и `/resolve`
разбирают неопределённую исходящую доставку с явным риском дубликата.
При активации проверить реальный диалог, поиск, два `/next`, перевод/страницу,
поздние картинку/MP3, местное расписание, канал и отзыв прав, второй аккаунт,
тестовый платёж и полный возврат. Подставной API не заменяет эти проверки.
