Тесты PostgreSQL используют синтетический корпус; приведённые выше 68 193 стиха относятся к отдельному настоящему импорту. Результат относится к проверенному коду, а не к любым будущим изменениям.

После добавления оформления локальный Windows-прогон завершился **431 passed, 26 skipped**: 18 PostgreSQL-тестов без включённого DB-окружения и 8 POSIX-сценариев, требующих Linux. Эти пропуски не учитываются как успешные тесты; полный набор выполнен отдельно на Linux, как указано выше.

Проверка `pip-audit 2.10.1` по 41 закреплённой Linux-зависимости завершилась без известных уязвимостей и без пропусков. Это проверка доступной базы advisory на момент запуска, а не тест проникновения или гарантия отсутствия неизвестных проблем. Обнаруженная в первоначальном наборе проблема старого pytest устранена обновлением до исправленной версии перед финальной фиксацией зависимостей.

В финальном развёртывании PostgreSQL, bot, worker и admin имеют статус healthy. Ответ на настоящий `/start` подтверждён оператором в ходе развёртывания. После обновления Bot API подтвердил имя, description, short description и 16 команд для default/ru/en, аватар профиля и меню команд. В БД сохранены 36 подтверждённых компонентов оформления. Фото нового `/start`, подпись, клавиатура и повторное использование `file_id` проверены автоматическими тестами; дополнительное подтверждение их вида в пользовательском клиенте учитывается отдельно.

Резервная копия реально восстановлена через `verify_backup.sh` в отдельную временную БД; полный аудит восстановленного корпуса прошёл, после чего временная БД удалена. Действующая БД этой проверкой не заменялась. Это подтверждает чтение и содержимое проверенного dump, но не отменяет согласования очереди с Telegram при восстановлении старого состояния в production.

Ежедневный systemd backup timer включён. Автоматическая отправка копий вне сервера и удаление старых dump не настроены этим таймером; оператор контролирует хранение и свободное место.

На реально импортированных Синодальном переводе и WEB проверены чтение, поиск, случайный стих, стих дня и все пять планов. Подтверждённый ответ `/start` и тесты подготовки отрывков не объявляются проверкой фактической публикации по расписанию: для неё требуется отдельный наблюдаемый запуск в разрешённом чате.

| Проверка | Что подтверждает | Где фиксировать результат |
|---|---|---|
| Модульные тесты | Парсинг, расписание, форматирование, политики и логика на тестовых данных. | Вывод pytest с числом passed/skipped и версией Python. |
| Контракты aiogram | Совместимость с реально установленной библиотекой. | Модуль `test_aiogram_contracts.py`; отсутствие библиотеки даёт skip. |
| PostgreSQL integration | Реальные миграции, транзакции, индексы и доставка с моделируемым Telegram. | `RUN_DB_TESTS=1`, вывод pytest, версия PostgreSQL. |
| Docker image/Compose | Сборка образа и исполнение процессов в целевом окружении. | Commit, digest/ID образа, `docker compose ps`. |
| Скачивание реального текста | Доступность выбранного источника, формат, лицензия и хеш. | Полный JSON receipt импорта. |
| PostgreSQL corpus audit | Наличие и согласованность реально записанного корпуса. | `app.cli audit`, `database_written` в receipt. |
| Healthchecks | Живость процессов, heartbeat, метаданные readiness. | `/health`, `/ready`, container health. |
| Advisory scan зависимостей | Известные уязвимости выбранных версий по доступной базе. | Версия сканера, список проверенных пакетов, число находок и пропусков. |
| Telegram | Получение команды и фактическая публикация в разрешённый чат. | Локальный отчёт оператора без токенов и персональных данных. |
| Backup/restore | Читаемость dump и восстановление в отдельную БД. | `verify_backup.sh`, checksum, аудит восстановленного корпуса. |
| Длительная эксплуатация | Поведение под реальной нагрузкой и после сбоев. | Отдельное наблюдение; короткий smoke-тест не является SLA. |

Итоговый отчёт конкретного развёртывания должен различать выполненные проверки, пропуски и оставшиеся ручные действия. Секреты, chat-ID, адрес сервера и пользовательские сообщения не нужны для публичного подтверждения результата.

## Воспроизведение тестов

В Python-окружении из [CONTRIBUTING](../CONTRIBUTING.md):

```bash
python -m pytest -o addopts= -q
python -m compileall -q app tests
```

На Linux Bash-сценарий `bash verify.sh` дополнительно проверяет shell-синтаксис и manifest, если он присутствует. Для PostgreSQL через подготовленную Compose-установку:

```bash
docker compose up -d postgres
# Дождитесь healthy PostgreSQL.
docker compose run --rm --no-deps -e RUN_DB_TESTS=1 bootstrap python -m pytest -o addopts= -q
```

Интеграционные тесты создают уникальные БД `biblebot_test_<UUID>` и удаляют именно их. Им нужна роль с правом `CREATE DATABASE`. Telegram-отправка и тексты внутри этих тестов моделируются, синтетический текст не является Писанием. На Windows POSIX shell-тесты могут быть пропущены; полный эксплуатационный сценарий проверяется на Linux.

## Проверка корпуса

```bash
sudo bash fill_database.sh discover --sources getbible --languages ru,en
sudo bash fill_database.sh --sources getbible --languages ru,en --editions getbible:synodal,getbible:web
sudo bash fill_database.sh status --full-report
docker compose run --rm --no-deps bootstrap python -m app.cli audit
```

Сохраняйте полный receipt с фактическими ID, количеством строк, source/content hashes, статусом и ошибками. Список кандидатов `discover` и результат `download` не заменяют `import` и аудит БД.

## Ручная приёмка Telegram

1. В своём личном чате выполните `/start`, `/settings`, `/translations`, `/language ru`, `/next`, `/random`, `/search любовь`.
2. Проверьте лицензионную подпись и несколько ссылок непосредственно по выбранному исходному изданию.
3. Настройте два собственных тестовых назначения на разные языки/время; проверьте их независимость.
4. Запланируйте публикацию, проверьте фактическое сообщение и `/status` после отправки.
5. Проверьте длинный отрывок из нескольких сообщений, паузу, продолжение и отписку.
6. В тестовой группе проверьте запрет управления неадминистратором и реакцию на потерю прав бота; при использовании форума проверьте нужную тему.
7. Восстановление dump проверяйте отдельно. Продукционный worker после возврата старой БД включается только после согласования состояния с Telegram.

Не отправляйте тесты в чужие чаты и не считайте наличие успешного `getMe` проверкой публикации по расписанию.

Офлайн-отчёт можно получить командой `python scripts/release_audit.py`: он сохраняется в `runtime-evidence/offline/` и не перезаписывает опубликованный `RELEASE-AUDIT.*`.


В 1.5.0 `test_devotional_artwork.py` проверяет три prompt-варианта, HTTP-параметры medium, неопределённые ошибки, AES-GCM и проверку SHA S3; `test_devotional_postgres.py` использует настоящие временные БД для фиксированного выбора стихов, сохранения фото, независимых часов и конкурирующего резерва последнего бюджета. Платный API и S3 этими unit/SQL-тестами не вызываются: фактическая эксплуатационная проверка фиксируется отдельно в RELEASE-AUDIT.
