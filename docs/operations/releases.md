# Выпуск версии

Выпуск — это тег `vX.Y.Z`, релиз на GitHub и образ в GHCR (`ghcr.io/xsenus/biblemessengerbot:X.Y.Z` и `:latest`).
Выкладка на VPS к выпуску не привязана: её делает автодеплой после каждого успешного CI `main`
([automatic-deploy.md](automatic-deploy.md)).

## Порядок

1. Отдельным PR поднимите версию: `VERSION`, `pyproject.toml`, тег образа в `docker-compose.yml` и строки
   версии в `app/` (`git grep -n "<старая версия>"`), а в `CHANGELOG.md` переименуйте «Не выпущено» в
   `## X.Y.Z — ГГГГ-ММ-ДД` и откройте новый пустой «Не выпущено». Влейте PR после зелёного CI.
2. Дождитесь успешного CI (Test) этого коммита на `main`.
3. Actions → **Release** → Run workflow, ветка `main`.

Workflow `release.yml`:

- берёт версию из `VERSION` и проверяет, что тега `vX.Y.Z` ещё нет;
- берёт текст релиза из раздела `## X.Y.Z — …` в `CHANGELOG.md` (пустой или отсутствующий раздел — ошибка);
- требует успешный CI (Test) для этого коммита `main`;
- собирает образ так же, как CI (`PROJECT_REVISION` = коммит), проверяет, что образ сообщает этот коммит, и
  сканирует его Trivy (критические уязвимости останавливают выпуск);
- публикует образ в GHCR как `X.Y.Z` и `latest`;
- только после этого создаёт тег `vX.Y.Z` на коммите и релиз на GitHub.

Если сбой произошёл до последнего шага, тег не создаётся, и workflow можно запустить снова.

## Почему не тег из консоли

Тег можно поставить и вручную (`git tag -a vX.Y.Z <коммит>` и `git push origin vX.Y.Z`): тогда образ публикует
шаг CI по тегу. Тег, созданный внутри Actions через `GITHUB_TOKEN`, другие workflow не запускает, поэтому
`release.yml` публикует образ сам.

Если в Settings → Rules → Rulesets есть правило, запрещающее создавать теги, добавьте в его исключения
GitHub Actions — иначе последний шаг завершится ошибкой (образ при этом уже опубликован).
