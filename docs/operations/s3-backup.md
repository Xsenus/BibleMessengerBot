# Резервные копии в S3

В `.env` задаются `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и `BACKUP_ENCRYPTION_KEY`. Ключ шифрования — 32 случайных байта в виде 64 hex-символов. Храните независимую приватную копию вне VPS и вне публичного Git. Без этого ключа восстановление зашифрованной БД невозможно.

Используются HTTPS, SigV4 и path-style; для Hostkey NL регион `nl`. [Документация Hostkey](https://hostkey.com/documentation/technical/exist_server_using/s3/). Приложение записывает только префикс `bible-messenger/v1/` указанного бакета, не меняет ACL и политики других объектов.

## Что сохраняется

`bash backup.sh` создаёт согласованный custom-format pg_dump, включая пользователей, расписания, очередь, библейские тексты и бинарные изображения. Перед загрузкой весь dump шифруется AES-256-GCM с новым nonce; затем проверяются HEAD и полный GET с SHA-256. Квитанция записывается в БД только после проверки. После успешной облачной проверки локально сохраняются до семи собственных снимков в пределах 4 GiB, минимум последний. Чужие файлы не очищаются. При ошибке S3 ротация не выполняется: контролируйте свободный диск и устраните причину ошибки. `BACKUP_LOCAL_ONLY=1 bash backup.sh` делает только локальный снимок.

Отдельный цикл `illustrator` копирует готовые изображения и JSON-манифесты с изданием, источником, адресом, SHA текста и prompt в S3; ошибка повторяется через 30 секунд, исходник остаётся в БД. Изображения не зашифрованы приложением, поэтому бакет должен оставаться приватным. Объекты имеют уникальные ключи; автоматического удаления старых облачных копий нет. Контролируйте объём и оплачиваемое хранение.

## Восстановление

В панели `/panel/` откройте **«Резервные копии»**: здесь показаны квитанции проверенных облачных копий БД (по 30 на страницу), дата создания снимка из имени штатного backup, дата проверки S3 и размер зашифрованного архива. Время отображается в часовом поясе браузера; для нестандартных имён неизвестная дата создания обозначена «—». Копии, сделанные только с `BACKUP_LOCAL_ONLY=1`, не имеют облачной квитанции и остаются в серверной папке `backups/`.

Панель показывает каталог сразу и затем сверяет открытые страницы с S3. Полный список ключей для префикса копий подтверждает отсутствие файла. Если список неполный, панель отдельно проверяет точный ключ. При ошибке доступа, тайм-ауте или расхождении метаданных запись сохраняется. «Обновить список» повторяет сверку.

Кнопка **«Удалить»** запрашивает подтверждение с именем файла. Сервер проверяет размер и контрольную сумму в метаданных, отправляет условный запрос удаления только для выбранного объекта и проверяет его отсутствие. Запись убирается после подтверждения S3. Действие регистрируется в журнале панели. Для сверки нужны права чтения объекта и списка корзины, для удаления дополнительно нужны права `DeleteObject`.

Нажмите **«Скачать .dump»**. Запрос авторизуется заголовком `X-Admin-Key`; ключ не передаётся в URL. Сервер проверит размер и SHA-256 архива из квитанции, аутентифицированно расшифрует AES-GCM и выдаст готовый PostgreSQL dump. Проверка и передача используют временные файлы и блоки; полный архив не помещается в оперативную память VPS. Временные файлы удаляются и при обрыве соединения. Одновременно сервер готовит/отдаёт одну копию; остальные запросы получают 409 и могут быть повторены после завершения. Перед подготовкой проверяется свободное место на диске. Ошибка проверки или отсутствие объекта S3 показываются в панели, файл не выдаётся. Интерфейс ждёт окончания скачивания, затем передаёт файл браузеру для сохранения. Скачивание не запускает восстановление и не меняет рабочую БД; доступ регистрируется в обычном журнале панели.

```bash
docker compose --profile maintenance run --rm -T --no-deps backup python -m app.backup_admin status
docker compose --profile maintenance run --rm -T --no-deps backup python -m app.backup_admin download-db --key bible-messenger/v1/database/EXACT_OBJECT_KEY --output /app/backups/recovered.dump
```

Команда скачивает, проверяет SHA-256 и аутентифицированно расшифровывает; существующий выходной файл не перезаписывает и рабочую БД не меняет. Перед восстановлением проверьте `pg_restore --list` и восстановите снимок в отдельную временную PostgreSQL-БД. Сравните количество изданий/стихов/иллюстраций и хеши изображений. Только после этого используйте существующий `restore.sh`, который явно останавливает службы и требует подтверждения замены рабочей БД.

Отдельные картинки восстанавливаются через манифест и `app.illustrations_admin add`, проверяющий текущий текст стиха; полный dump восстанавливает их автоматически. Секреты `.env` в dump не входят: нужны отдельные приватные копии конфигурации, ключа шифрования и сведения о commit приложения.

Для установки Docker ежедневный `bible-messenger-backup.timer` запускает `backup.sh` в 01:30–01:35 Asia/Novosibirsk. Скопируйте units из `deploy/` по [operations.md](operations.md), задав путь проекта и часовой пояс. Проверяйте `systemctl list-timers --all bible-messenger-backup.timer` и журнал соответствующей service. Наличие timer не заменяет периодическую пробу восстановления.

Для нативной установки systemd с PostgreSQL на хосте установите отдельную службу. Она использует действующий выпуск и его Python-окружение, параметры подключения из `runtime.env`, ключи S3 из `s3.env` и существующий `bible-systemd-ops`. Дамп создаётся однопоточно от роли приложения. Общая блокировка с автодеплоем исключает смену выпуска во время резервирования. Локальная ротация выполняется после подтверждённой загрузки и полного чтения архива обратно из S3. Лимиты службы ограничивают CPU и память на малом VPS.

```bash
sudo install -m 0755 deploy/backup-systemd.sh /usr/local/sbin/bible-backup
sudo install -m 0644 deploy/bible-messenger-backup-native.service deploy/bible-messenger-backup-native.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bible-messenger-backup-native.timer
sudo systemctl start --no-block bible-messenger-backup-native.service
sudo systemctl list-timers --all bible-messenger-backup-native.timer
sudo journalctl -u bible-messenger-backup-native.service
```

Расписание нативного таймера — ежедневно в 01:30–01:35 по Новосибирску с выполнением пропущенного запуска после простоя. Успешный запуск должен завершиться строками `"status": "verified"` и `Backup complete`. Копии находятся вне каталогов выпусков, в `/opt/bible-messenger-bot/backups/`, и доступны через обычный каталог резервных копий панели.

Успешный локальный `Database backup: ...` ещё не подтверждает выгрузку в S3: в журнале должны присутствовать `status: verified` и успешное завершение service. Файлы на VPS находятся в `/opt/bible-messenger-bot/backups/`, облачные дампы — под префиксом `bible-messenger/v1/database/`. Облачные квитанции доступны в разделе «Резервные копии» панели и через `backup_admin status`. Если после сборки из checkout с `umask 077` возникает `PermissionError` при импорте `backup_admin`, пересоберите образ с актуальным Dockerfile: права исходного кода нормализуются при сборке, секреты и сами dump остаются приватными.

Начиная с 1.6.0 в копии входят все версии картинок, времена создания и версия prompt, история подтверждённых отправок и ожидания фото. S3-манифест каждой версии включает `generated_at` и `prompt_version`; обновление Telegram-кэша не меняет возраст версии.

Начиная с 1.7.0 dump также сохраняет ID исходных Telegram-карточек, полные снимки стихов и очередь их редактирования. Проверка восстановления должна сопоставлять ID подтверждённого редактирования с исходным сообщением и проверять наличие снимков всего отрывка; результат текущей пробы приведён в [аудите выпуска](../../RELEASE-AUDIT.md).
