# Автоматическое обновление VPS

После успешного workflow `Test` для **push в main** GitHub запускает `Deploy production`.
Проверки PR, форков, тегов и других веток не дают доступа к серверу. Сценарий не скачивает
артефакты и не выполняет checkout в привилегированном job. На VPS передаётся только полный
SHA проверенного коммита. Если он уже не является текущей `origin/main`, запрос пропускается;
следующий успешный CI обновит последнюю main. Новая main, появившаяся во время уже начатого
обновления, устанавливается следующим запуском после собственного CI.

## Однократная установка

Рабочий каталог — `/opt/bible-messenger-bot`, SSH-пользователь — `bibledeploy`.
На сервере должны работать systemd, Docker Compose, Git, sudo и flock. Уже существующие
`.env`, сертификаты, тома и пользователи приложения сохраняются.

1. Создайте отдельный Ed25519-ключ для GitHub Actions, не используя root-пароль или личный ключ.
2. После слияния скопируйте на VPS **только публичный** ключ и выполните от root:

   ```bash
   cd /opt/bible-messenger-bot
   bash deploy/install-auto-deploy.sh /root/bible-deploy.pub
   ```

   Установщик создаёт отдельного пользователя, принудительную SSH-команду и правило sudo
   только для `bible-auto-deploy submit`. SCP, shell, PTY и перенаправление портов запрещены.
   Допускается ровно один SHA из 40 строчных шестнадцатеричных символов. Обработчик устанавливается
   вне checkout, под root; его будущие изменения нужно устанавливать повторно после проверки.

3. В GitHub Environment **production** разрешите только main, без обязательного ручного
   подтверждения для штатного автоматического обновления. Задайте:

   | Тип | Имя | Значение |
   |---|---|---|
   | Variable | `VPS_HOST` | Адрес VPS |
   | Secret | `VPS_SSH_KEY` | Приватный ключ Ed25519 |
   | Secret | `VPS_KNOWN_HOSTS` | Проверенная запись ключа SSH-хоста |

   Отпечаток хоста проверяют по доверенному существующему SSH-соединению. Не заменяйте
   проверку на `StrictHostKeyChecking=no` или непроверенный `ssh-keyscan` при каждом деплое.
   Приватный ключ не должен попадать в Git, журнал или артефакты. Удаление его публичной
   записи из `/var/lib/bible-deploy/.ssh/authorized_keys` немедленно отключает доступ.

## Порядок обновления

- GitHub допускает один активный деплой; `flock` дополнительно сериализует запуск на сервере.
- systemd исполняет работу независимо от SSH: разрыв соединения или отмена Actions не
  оставляет обновление оборванным посередине. Общий предел службы — 80 минут.
- Проверяются чистота checkout, ветка, точный SHA main, здоровье работающих обработчиков,
  действующий PostgreSQL и отпечаток применённых миграций.
- Прежние образы получают теги `rollback-<SHA>-<service>`. До изменения кода создаётся
  штатная копия БД с загрузкой и проверкой в настроенном S3. Сбой backup прекращает деплой.
- Выполняется штатный `rolling-update.sh --yes`: сборка, подготовка голосов, проверка и
  применение миграций, последовательное обновление **только ранее работавших** служб.
- Проверяются здоровье, `/ready`, миграции, сохранность `.env` и ID контейнера PostgreSQL.
  Отключённые MAX/VK не включаются; VPN, шлюз и PostgreSQL не перезапускаются.

Журналы и приватные подтверждения находятся в `runtime-evidence/auto-deploy/` (umask 077).
Файл `deployed-commit` содержит последний успешно установленный SHA, каждый запуск сохраняет
свой exit code и снимки служб. GitHub показывает результат и ссылку на панель в Environment.

```bash
cat /opt/bible-messenger-bot/runtime-evidence/auto-deploy/deployed-commit
journalctl -u 'bible-auto-deploy-*' --since today
```

## Ошибки и откат

### Отображение в админке

Раздел «Состояние → Версия и автодеплой» читает `runtime-evidence/deploy-status/status.json`.
Это отдельный каталог с единственной публичной квитанцией: директория 755, JSON 644,
владелец root. Обновление выполняется через атомарную замену файла. В Compose каталог
подключён **только к admin** как `/app/deploy-status:ro`; весь `runtime-evidence` подключать нельзя.
При новом сбое прежняя успешная установка сохраняется отдельно от последней попытки.

`rolling-update.sh` передаёт Git SHA сборке через `PROJECT_REVISION`. В образе создаются
`BUILD-METADATA.json` и OCI label `org.opencontainers.image.revision`. Перед подтверждением
успеха автодеплой проверяет этот label у каждой обновлённой службы. Обычная сборка без Git SHA
покажет неизвестный коммит; он не берётся из checkout хоста. Новых переменных в `.env` нет.

После обновления механизма установите новую версию root-сценария и писателя квитанции:
повторите `install-auto-deploy.sh` с прежним публичным ключом, уже после слияния и до первого
деплоя новой версии. Установщик добавляет `/usr/local/libexec/bible-deploy-status` и публичный
каталог. Приватный ключ и настройки GitHub менять не требуется. Запущенный деплой нельзя
обновлять посередине — дождитесь завершения systemd-службы перед повторной установкой.

При сбое **и неизменной схеме** автоматически возвращаются предыдущие исходники и образы
только ранее работавших служб. Checkout становится detached на прежнем SHA; ветки и история
не переписываются. Следующий успешный деплой возвращает main. Ошибка отката остаётся ошибкой
в Actions; успешный откат также не выдаётся за успешную установку нового коммита.

Если миграции уже изменили схему или проверить её нельзя, обработчики останавливаются,
автоматического восстановления dump **нет**. Оператор проверяет журнал, совместимость кода
и резервную копию. Автоматическое восстановление старого dump потеряло бы новые сообщения
и платежи; процедура описана в [operations.md](operations.md).

Для повторной попытки используйте **Re-run all jobs** успешного CI `Test` текущей main:
завершение повторного CI снова запускает деплой. Для отключения используйте **Disable workflow**
у `Deploy production`; уже работающая systemd-служба продолжит работу до завершения.
Ручное обновление нельзя запускать параллельно с автоматическим. Следите за свободным диском:
сохранённые rollback-образы не удаляются глобальным Docker prune и требуют контролируемой
ротации оператором, как и прежние ручные образы.
