# Инструкции для агентов

Файл читают Codex (напрямую) и Claude Code (через `@AGENTS.md` в `CLAUDE.md`). Правила храним только здесь.
Общие правила разработки, тестов и комментариев в коде — в [CONTRIBUTING.md](CONTRIBUTING.md).

## Git: ветки и Pull Request'ы

Обязательно для всех агентов (Codex, Claude Code) и людей. PR — Pull Request (в GitLab — Merge Request). Базовая ветка: `main`.

### Ветки
- Любое изменение — даже одна строка или документация — делается в новой ветке от свежей `main`: `git fetch`, затем ветка от `origin/main`.
- Одна задача — одна ветка. Имя — по схеме, принятой в репозитории, иначе `feature/…`, `fix/…`, `chore/…`.
- Перед созданием ветки проверь `git status`: чужие незакоммиченные изменения не трогай и не переноси в свою ветку — спроси.
- В чужие ветки, включая ветки другого агента, без запроса не коммить. Если Codex и Claude работают одновременно, у каждого своя ветка и свой worktree или клон.
- Прямые коммиты и пуши в `main` запрещены.

### Мерж — только через PR
- Изменения попадают в `main` только через PR. Запрещено: локальный `git merge` в `main` с последующим push, прямой push, force-push в общие ветки, мерж в обход защиты ветки (`--admin` и т. п.).
- Перед открытием PR прогони «Проверки перед PR». Не пиши, что проверки прошли, если ты их не запускал.
- В описании PR: что сделано и зачем, как проверено, есть ли миграции БД.
- Открыв PR, дождись результатов CI (`gh pr checks <номер> --watch` или аналог).
- PR вливается, только когда проверки зелёные (если CI нет — локальные), конфликтов нет и получены обязательные ревью. Способ мержа (squash / merge / rebase) — как принято в репозитории.
- Кто вливает: агент сам, через PR (`gh pr merge` или аналог), как только выполнены условия выше.
- Если для push или создания PR нужно подтверждение — запроси его. Если это невозможно (нет сети, прав или CLI), не обходи локальным мержем: доведи ветку до зелёных локальных проверок и в ответе дай имя ветки, заголовок и описание PR. Если среда сама создаёт ветку и PR (облачные задачи Codex и Claude Code) — пользуйся её механизмом.

### Если проверки (локальные или CI) или мерж не проходят
- Цель — зелёный PR за счёт исправления причины, а не обхода проверок.
- Читай логи упавших джобов (`gh run view <id> --log-failed` или аналог), воспроизводи падение локально той же командой, что в CI, ищи корневую причину.
- Исправляй код, а не проверки. Без явного разрешения пользователя нельзя: пропускать, удалять или ослаблять тесты; добавлять подавления ради зелёного статуса (`@ts-ignore`, `eslint-disable`, `# type: ignore`, `# noqa`, `#pragma warning disable`, skip у тестов); снижать пороги (покрытие и т. п.); править конфиги CI и линтеров, чтобы стало зелёным; коммитить с `--no-verify`.
- Тест устарел из-за намеренного изменения поведения — обнови его и объясни это в описании PR.
- Конфликты: подтяни свежую `main` в свою ветку, разреши конфликты, сохранив чужие изменения, снова прогони проверки. После rebase — только `git push --force-with-lease` и только в свою ветку.
- Исправления пушь в ту же ветку, новый PR не создавай.
- Падение не связано с твоими изменениями (то же падает на `main`, флейк, инфраструктура, секреты CI) — не маскируй его: перезапусти джоб один раз, не помогло — сообщи с диагнозом.
- После трёх циклов исправлений проверки всё ещё красные — остановись и опиши, что пробовал и в чём, по-твоему, причина.

### После мержа: удаление веток
- Удаляй ветку, только когда она полностью отработана: PR в статусе merged (`gh pr view <номер> --json state` или аналог), работы по ней не осталось и других открытых PR из неё нет.
- Удалённую ветку удали, если хостинг не сделал этого сам: `git push origin --delete <ветка>`.
- Локально: `git switch main && git pull --ff-only`, затем `git branch -d <ветка>`. После squash- или rebase-мержа git может отказаться — тогда, убедившись, что PR merged, используй `-D`. В конце `git fetch --prune`.
- Слитую ветку не переиспользуй: доработки и исправления после мержа — в новой ветке от свежей `main`.
- Никогда не удаляй `main`, защищённые и чужие ветки, а также ветки с открытыми PR или с коммитами, не вошедшими в слитый PR.

### БД и миграции
- Схему БД меняй только через миграции проекта: новый файл `sql/migrations/NNN_описание.sql` (следующий номер), в той же ветке и том же PR, что и код. Уже применённые миграции не редактируй — их SHA-256 записан в `schema_migrations`.
- Проверить, какие миграции ожидают применения, не меняя базу: `python -m app.cli migrate --check` (код 3 — есть ожидающие).
- Из рабочей ветки ничего не применяй к общим и боевым базам.

### Проверки перед PR
Те же команды, что в CI (`.github/workflows/ci.yml`), Python 3.12 (CI также проверяет 3.14).

Бэкенд (Python) — линтер, типы, синтаксис:
```bash
python -m pip install -c constraints-linux.txt -r requirements-dev.txt
ruff check .
mypy
find . -path ./admin-ui/node_modules -prune -o -name '*.sh' -print0 | xargs -0 -r -n1 bash -n
python -m compileall -q app tests scripts
```

Бэкенд — тесты (нужны PostgreSQL 16 с ролью, которая может создавать временные БД, и пакеты `espeak-ng ffmpeg tesseract-ocr tesseract-ocr-rus`; порог покрытия 75 %):
```bash
python -m pip install -c constraints-linux.txt -r requirements-dev.txt -r requirements-test.txt
python -m pip check
RUN_DB_TESTS=1 DATABASE_URL=postgresql://<user>:<password>@localhost:5432/<db> python -m pytest -o addopts= -q --cov=app
```
Без `RUN_DB_TESTS=1` тесты с PostgreSQL пропускаются — пропуски не считаются пройденными. Нейронные голоса CI проверяет дополнительно (`pip install -r requirements-neural.txt`, `python -m app.neural_audio_admin prepare`, `RUN_NEURAL_TESTS=1`).

Зависимости (как в CI):
```bash
sed 's/+cpu$//' constraints-neural-linux.txt > /tmp/neural-audit.txt
pip-audit --no-deps --disable-pip --strict -r constraints-linux.txt -r /tmp/neural-audit.txt
```

Веб-панель (`admin-ui`, React + Vite). Линтера и тестов у панели нет — проверяется установка, аудит и сборка:
```bash
npm ci --prefix admin-ui
npm audit --prefix admin-ui --audit-level=moderate
npm run build --prefix admin-ui
```

Docker (джоб `image` в CI; локально — если есть Docker): `cp .env.example .env && docker compose --profile '*' config --quiet`, затем сборка образа `docker build .`.
